1. INPUTS, ORIGINAL HISTORY, AND TOOL IDENTITY

The new request has an exact field set, external SHA pin and size bounds.
It binds the original request unchanged, every original journal file and
the final journal-chain digest, the failed run/job/artifact identity, and
the new recovery tool commit/hash/helper hashes. Original evidence is read
through confined plain paths and checked against its prior exact request;
pack/restore/import evidence preserves the original source/base identities
and the false full-certificate claim. It does not require or pretend to
rehash a local 1.3GB archive in this recovery preflight. The two subsequent
remote full downloads establish the current remote content identity.

The original journal is required to be precisely the pinned file set. Its
26 consecutive events, raw-response hashes, start/request/source/tool/run
bindings, failed endpoint, exactly three POST intents, and recorded created
release/asset ids are validated. The captured final draft and asset metadata
are normalized through the new URL protocol and retained for comparison
with the actual prepublication snapshot. No previous publication PATCH is
silently adopted as a clean draft state.

I identified an intermediate deployment bug: checking every helper under

and original P remains unchanged in the old request. Run attempts other
than one are rejected before any HTTP call.

2. MUTATION BOUNDARY AND TWO FULL DOWNLOADS

RecoveryHTTP.mutate rejects every operation except a single PATCH to its
bound release id with the exact body {draft:false}; archive and upload-name
arguments must be absent, and writes must still be zero. The inherited
sender records and fsyncs the intent before sending and does not retry or
follow mutation redirects. The broad old publisher is imported for reviewed
utilities but its create/upload publish routine is not invoked.

Each snapshot reads the pinned release, pinned asset, and dedicated assets
collection with per_page=100,page=1, then checks the exact lightweight tag.
The required collection has exactly one row, so this short page proves the
expected complete singleton under the API pagination contract. Both it and
the release's embedded row must match the individually fetched asset on all
identity fields. A long or extra collection is rejected, not truncated into
an apparent singleton. This protocol is deliberately not a 250-asset list
implementation.

The draft snapshot must exactly match the captured stable release and asset
fields. The new helper validates API URLs and phase-specific presentation
URLs: the captured untagged slug is allowed for a draft and its asset must
use that same slug. Presentation URLs are never download authority. Binary
downloads use the pinned repository/asset id and the already reviewed
bounded-stream, exact-length/SHA256 reader with credential-stripped approved
redirects. The original fixed final-tag URL requirement remains in force
once published.

After the first complete asset-id download, local inputs/tools and live
origin identities are rechecked, and another complete draft snapshot must
match. Only then is the one PATCH issued. The postpublication snapshot must
have the same pinned ids, content, target, title, false prerelease flag and
canonical final URLs; its body must also match the original reviewed scope.
A second complete binary download follows. A final snapshot must equal the
initial published snapshot, and another local/tool recheck precedes result
creation. Download counts are appropriately omitted from stable equality.

3. FAILURE AND RESULT SEMANTICS

An already published object at entry is rejected. A timeout or lost PATCH
response, changed published metadata, corrupt second download, or changed
inputs enters the failure path: there is no retry, second publication,
delete, rollback, tag mutation, upload, or success record. Remote state is
left intact for a separately reviewed reconciliation. The one-write count
does not misattribute the old three POSTs to this recovery.

The output retains the standard durable-core-release record schema and adds
explicit recovery provenance. The record identifies both full downloads,
final metadata response hashes, new tool/request/actions identity, original
request/tool/journal/failed execution, and the observed immutable flag.
Fixture output is fixture_only and remote_durability_verified=false; actual
Lean execution and full-certificate proof remain false in all branches.
Result bytes and parent directory are fsynced by the reviewed durability
utility, and the result hash enters the final journal. This does not claim
survival of complete ephemeral-runner loss.

The unavoidable external concurrency limitation in the protocol review
still applies: GET and PATCH are separate remote requests. Before/after
checks detect changed observed state but are not a hash-conditional atomic
GitHub transaction. No code path promises such atomicity or permanent
immutability. The future workflow must also bind the actual request and
tool revision and use the intended serialized execution scope.
