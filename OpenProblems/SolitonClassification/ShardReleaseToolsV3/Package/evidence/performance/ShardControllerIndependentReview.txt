Commit and input binding
The production check compares every exact runtime Python helper against its
actual committed blob, rejects extra/nested Python files and cached inputs,
and requires the actual tool HEAD to equal the request's publisher revision P.
The input checkout is separately required to be the Git root at GITHUB_SHA Q.
Each request, catalog, full plan and all 250 plan checkpoint files must both
match its pinned digest and equal its actual Q blob. P and Q are distinct.
There is no literal Q embedded in its own input commit. The local Q comparison
is explicitly only same-execution consistency; independent post-commit/run
head verification remains an external deployment responsibility.

bound_plan actually validates the complete canonical 250-job plan, its signed
partition, candidate/protocol metadata and chained checkpoint attachments.
prepare adds each checkpoint to the immutable pin map: 3 input files plus
250 checkpoints. recheck covers that entire map between stages and at exit.
The final source diff adds only comments and one recheck after the potentially
long complete output hashing pass, before either successful receipt is written.
That is the correct location for detecting changes during the last traversal.
These are staged consistency checks, not an atomic filesystem lock against an
adversarial concurrent process after the final check.

Actual interfaces and control flow
execute constructs the fixed public d.prepare / d.download_with_budget and
v.prepare / v.publish_with_budget phases. It does not accept fixture hooks,
construct an alternative HTTP client, invoke private publish methods or bypass
the publisher's quota gate. Both prepares receive the same original six-tuple;
the actual downloaded archives directory is passed directly into v.prepare.
That frozen public prepare calls the complete original-archive preflight624.
The controller then verifies status, exact requested order/coverage, input
hashes and original archive identities before publication can begin.

Returned publication evidence is checked against its saved summary, N+3
mutation count, source/plan/request/catalog/base/tool identities, ordered keys,
durable record bytes and production record schema. Journal sequence and hash
links, raw response hashes, exact file inventory and earlier-stage preservation
are checked before final success. The controller makes no extra REST requests.
Its final receipt remains partial scope, with full_certificate_proved false;
it does not turn publication into a complete numerical or Lean theorem.

Failure and credential treatment
A failed download/preflight prevents the subsequent publication call. A failed
publisher or final check is not retried and triggers no remote cleanup. Local
failure evidence records phase and whether publication started/returned;
it deliberately does not infer zero remote writes after an attempted call.
Existing summary/journal/original files are retained. Failed evidence writes
cannot convert the original exception into success. The controller records
exception type/status rather than an arbitrary error string, and does not
serialize the supplied token or environment. Production credentials only flow
to the two fixed public libraries; fixture credentials are explicit constants.

Validation boundary
The original retained report records success and 14 rejecting cases, including
earlier-stage failure, changed inputs/evidence, fixture-to-production rejection,
and real local Git clean/dirty tool and Q checks. Its phase implementations are
orchestration stubs: synthetic fixture preflight/summary fields are NOT actual
archive preflight, HTTP, mutation or durability observations.
The new narrow report additionally records late request/checkpoint changes
injected only after the final exact-files traversal, both rejected before any
success receipt, while retaining the fixture publication summary. It checks a
real local Git checkout built from the full 253 prepare pins, accepts its clean
identity and rejects a dirty checkpoint. I read these test implementations and
their retained reports/console, and independently checked their source hashes;
I did not independently rerun either process or observe its process exit code.
The runtime diff and these narrow cases address the final traversal gap without
changing the frozen network protocol. No production network/full-preflight run,
new Lean execution, real catalog or deployment YAML is established by them.
